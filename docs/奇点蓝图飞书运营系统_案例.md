# 把战队运营搬进飞书：多维表格 + 机器人 + 面板的轻量方案

**案例对象**：辽宁工程技术大学「奇点蓝图」RoboMaster 战队 ｜ 2026.08 – 至今 ｜ 个人主导
**一句话**：不新开系统，把任务、提案、物料、合同四条链路收进飞书——表单做入口、多维表格做数据、自动化做流程、机器人做交互、面板做大屏。

---

## 一、摘要

| 项 | 内容 |
|---|---|
| 问题 | 16 人四方向梯队，任务靠群消息、库存靠 Excel、赞助合同靠记忆；队长成了人肉路由器 |
| 方案 | 以飞书多维表格为唯一数据源，向上接表单、自动化、机器人与展示面板 |
| 结果 | 2 张表单、6 条自动化、3 个业务机器人、1 个任务面板；任务卡片、每日催办、提案审批在飞书内闭环 |

## 二、场景与约束

学生组织没有行政约束力，成员分布在机械、电控、软件、视觉四个方向，作息和投入度差异很大。三件事最容易掉地上：

1. **任务派了没人跟**：群里 @ 一下就算派发，截止日期靠记忆，催办靠队长逐个私聊；
2. **物料账对不上**：元器件用 Excel 台账，查一颗料要翻表、问人，采购过的件重复买；
3. **信息不回流**：队员有技术想法，但没有低成本的上报入口；提案和任务混在一起，无法区分。

约束决定了方案形态：**不新增系统、不改变成员习惯**。成员已经在飞书里，所以入口必须是飞书；队长只有一个人，所以流程必须自动跑。

## 三、方案总览：四层结构

```
入口层    任务派发表单 │ 技术提案表单 │ 战队群 │ 机器人私聊
                ↓              ↓            ↓
数据层    飞书多维表格（任务 / 提案同表，用「记录类型」区分）
                ↓
流程层    6 条自动化：群发提醒 · 私发执行人 · 完成通知 · 每日催办
                     · 提案提交通知 · 审批结果通知
                ↓
交互层    任务卡片（✓ 标记完成 / ✓ 通过 / ✕ 驳回）· BOM / 采购 / 赞助机器人
                ↓
展示层    Flask 任务面板（读多维表格 + GitHub 贡献榜，实验室大屏）
```

四层里，**数据层只有一个源**：所有入口写进同一张多维表格，所有展示和通知都从这张表读。这样新增一条链路时，不需要再建一套数据。

## 四、四条链路

### 链路 A：任务派发（自上而下）

**流转**：管理员填「任务派发（管理员）」表单 → 多维表格新增记录 → ① 群发卡片到 2027 赛季步兵 / 哨兵群 → ② 私发执行人，卡片带「✓ 标记完成」→ 点击后回写「完成情况 = 已完成」→ ③ 通知群与发布人 → ④ 每天 09:00 查未完成记录，私信催办。

**关键设计**：
- 卡片按钮用多维表格的 `setRecord` 直接改单选值，不引入外部服务，点击即闭环；
- 催办只发执行人、不发群，避免公开施压；
- 截止日期、优先级、附件都留在记录里，群消息只承担提醒，不承担存档。

**证据**：10-01 17:06 发出「📌 你有一个新任务」；10-02 至 10-05 每天 09:00 连续发出「⏰ 任务未完成提醒」；09-29 测试任务点击「✓ 标记完成」后，群与发布人收到「✅ 任务已完成」。

### 链路 B：技术提案（自下而上）

**流转**：任何队员填「技术提案」表单（记录类型固定为「技术提案」）→ 自动化把「审核状态」改为「待审核」→ 私信队长，卡片带「✓ 通过」「✕ 驳回」→ 点击回写审核状态 → 通知提案人 → 通过的提案由队长手动转成正式任务。

**关键设计**：
- **同表加字段，不新建表**：新增「记录类型」「审核状态」两个字段，避免多表维护成本；历史记录用 `!t ||` 兜底；
- **审批只提醒、不自动建任务**：避免把没想清楚的想法直接变成排期，决策权留在队长；
- **提案不上大屏**：待评审信息不适合公屏展示，查看与审批都在多维表格里完成；
- 通知目标写成独立配置项，后续从「私信队长」改成「发管理群」只动一处。

**证据**：09-29 17:19 收到「💡 有新的技术提案待审批」；一条提案已完成审批（审核状态 = 已通过）。

### 链路 C：BOM 库存机器人

**流转**：群里上传 BOM（Excel / CSV）→ 选「加入库存」或「摘取物料」→ 与现有库存对比，生成精简 BOM → 入库并同步飞书多维表格 → 支持「查询 / 历史 / 删除 / 授权 / 谁有 / 库存」等命令。

**技术要点**：
- 飞书**长连接**（lark-oapi），纯出站 WebSocket，不需要公网回调；Flask Webhook 仅作备选；
- 会话状态机 5 个状态，覆盖「文件已上传 → 选模式 → 确认 → 完成」；
- AI 兜底（OpenRouter）做去重与命名标准化，失败时降级到本地规则，不阻断主流程；
- 删除按批次回滚，避免误删整库；
- 库存同步到多维表格，机器人对话与表格视图看同一份数据。

**我的改造**：接管开源项目的后端判断逻辑，补上「成员提想法 → 队长审批 → 结果回访」的反馈闭环；把这套「长连接 + 状态机 + 表格同步」的模板抽象出来。

### 链路 D：采购与赞助合同

- **采购机器人**：申请 → 审批 → 到货验收，机器人做状态查询与提醒（代码完成，尚未上线）；
- **赞助合同机器人**：合同「草稿 / 生效中 / 已完成 / 已终止」状态机，多步引导录入，同步多维表格；09-24 完成长连接联机验证。

## 五、面板与部署

**任务面板**（Flask）：
- `/api/feishu` 分页拉取多维表格全量记录（每页 500 条，最多 10 页）；
- `/api/github` 汇总组织仓库贡献榜与动态，10 分钟文件缓存，节省 API 配额；
- 前端是赛博风大屏，挂在实验室显示器上，任务总数、待办排行、DDL 倒计时实时刷新。

**进程守护**：
- Windows 侧用 `run_all.py` 一个进程管三个机器人：子进程崩溃自动重启、单实例锁防止同一应用两条长连接互相抢消息；
- 上云方案：阿里云 ECS 学生机 + 三个 systemd 服务（面板 / BOM / 赞助），5010 高位端口绕开备案；代码零改动，密钥单独 scp。

**运行方式**：任务后台的 6 条自动化在飞书云端常驻；三个业务机器人走飞书长连接，已验证可正常连上并按需启动。

## 六、结果与证据

| 维度 | 数字 / 状态 | 证据 |
|---|---|---|
| 数据 | 16 条记录、10 个字段、2 张表单 | 多维表格「奇点蓝图任务管理后台」 |
| 流程 | 6 条自动化全部启用 | 群发 / 私发 / 完成通知 / 每日催办 / 提案通知 / 审批结果 |
| 交互 | 3 个业务机器人 | BOM、采购、赞助；任务后台另有独立应用 |
| 覆盖 | 3 个战队群 | 2027 赛季步兵、哨兵、硬件组 |
| 运行 | 连续 4 天每日 09:00 催办 | 10-02 – 10-05 私信卡片 |
| 闭环 | 任务完成、提案审批均可回写 | 09-29 两条卡片记录 |

## 七、如果换到制造业：这套东西怎么迁移

| 制造业场景 | 本案例对应物 | 可直接复用的部分 |
|---|---|---|
| 研发 | 任务派发 + 技术提案双通道 | 同表双记录类型、审批卡片、结果回写 |
| 生产 | 缺料上报、线边库查询 | BOM 库存机器人的查询 / 报缺 / 回滚 |
| 供应 | BOM 解析、采购申请 | BOM 机器人 + 采购机器人的状态机 |
| 销售 | 赞助合同跟踪 | 合同状态机（可换为客户合同 / 回款） |
| 服务 | 群内答疑 | 机器人问答 + 知识库沉淀 |

换行业时不需要重写系统，需要重写的是**字段、审批规则和话术**——这正是解决方案岗要做的翻译工作。

## 八、复盘

**做对了**：
1. 先跑通一条链路（任务派发），再复制到提案、库存、合同，避免一次性设计过大；
2. 入口放在成员已经在用的飞书里，推广成本接近零；
3. 同表加字段而不是新建表，自动化和面板只改一处；
4. 卡片按钮直接改记录，不引入额外服务，点击即闭环。

**不足**：
1. 使用量小：16 条记录里含测试数据，真实任务只有个位数；
2. BOM 主数据还可进一步收敛到多维表格，当前是本地 JSON + 云表格同步；
3. 机器人按需启动，缺少健康检查与告警；
4. 权限只做到名单级（删除 / 管理员），没有按角色细分。

**下一步**：把 BOM 主数据迁到多维表格、加健康检查与告警、把「任务按时完成率 / 提案通过率」做成面板指标。
